# Plan Técnico: Plan General Contable (PGC) Español — Módulo Multi-tenant

**Feature**: `001-plan-general-contable`
**Stack**: PostgreSQL 16+ · FastAPI (async, SQLModel/SQLAlchemy) · Next.js (TypeScript)
**Referencias**: `spec.md` (SPEC-001) · `constitution.md` v1.0.0
**Fecha**: 2026-09-16
**Estado**: Implementación parcial: migraciones, seed, árbol de cuentas y consulta de sugerencias verificadas; alta, edición/protección completa y frontend del PGC permanecen pendientes.

Este documento detalla la arquitectura de implementación del Plan General Contable
español como base del módulo contable multiempresa. Todo diseño sigue estrictamente
la `constitution.md`: multi-tenancy por `tenant_id`, precisión decimal
(`Decimal` / `NUMERIC(18,4)`), auditoría inmutable en la misma transacción ACID y
pruebas obligatorias (balance estricto + aislamiento entre empresas).

Nota de alcance: la SPEC-001 asume en su sección *Assumptions* que la carga de un
catálogo estándar (seed) queda fuera de su alcance. Este plan **amplía** dicha
decisión: se define un mecanismo de seeding automático por tenant (requisito del
usuario), manteniendo la alta manual de subcuentas como funcionalidad abierta.

---

## 1. Estructura jerárquica de 5 niveles del PGC

El PGC español se modela como un árbol de cuentas con **hasta 5 niveles** de
profundidad. El nivel se deriva de la **longitud del código** (1 dígito por nivel), y
la rama completa se encadena por `parent_id`:

| Nivel | Longitud código | Denominación PGC | Ejemplo |
|-------|-----------------|------------------|---------|
| 1 | 1 dígito | Grupo | `1` (Financiación básica) |
| 2 | 2 dígitos | Subgrupo | `11` (Fondos propios) |
| 3 | 3 dígitos | Cuenta (3 dígitos) | `111` (Patrimonio neto) |
| 4 | 4 dígitos | Subcuenta | `1110` (Patrimonio neto c/p) |
| 5 | 5 a 8 dígitos | Subcuenta auxiliar | `11100001` (Patrimonio neto - socio A) |

Reglas estructurales (validar en backend + constraints DB):

1. **Nivel = longitud del código** en niveles 1-4; el nivel 5 admite códigos de 5 a 8
   dígitos (subcuentas auxiliares). Nunca más de 8 dígitos.
2. **Profundidad máxima 5**: una cuenta de nivel 5 no admite hijas (SC-003/SC-006 de
   la spec, FR-006).
3. **Hojas apuntables**: `is_selectable = true` solo en cuentas de último nivel de su
   rama (sin hijas) que además sean **subcuentas** (nivel ≥ 4). Los grupos/subgrupos/
   cuentas de 1-3 dígitos y cualquier cuenta con descendencia son `is_selectable = false`.
4. **Prefijo jerárquico**: el código de una hija comienza por el código del padre
   (`'43000001'` cuelga de `'4300'`, que cuelga de `'430'`).
5. **Código único por empresa**: `UNIQUE (tenant_id, code)`.

Ajuste frente a la spec: el criterio *fr-005* dice "hojas apuntables"; se concreta en
"hojas con nivel ≥ 4" para impedir asientos sobre cuentas de cargo de 1-3 dígitos
(véase §5).

## 2. Definición SQL: tabla `account_plan`

DDL completo con multi-tenancy obligatorio y todas las restricciones (§5).

```sql
-- ============================================================
--  Tabla de cuentas contables del PGC (multi-tenant)
-- ============================================================
BEGIN;

CREATE TABLE IF NOT EXISTS account_plan (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id     BIGINT       NOT NULL,                    -- empresa activa (aislamiento)
    code          VARCHAR(8)   NOT NULL,                    -- código numérico 1..8 dígitos
    name          VARCHAR(200) NOT NULL,                    -- descripción de la cuenta
    parent_id     BIGINT,                                   -- cuenta padre (NULL solo nivel 1)
    level         SMALLINT     NOT NULL CHECK (level BETWEEN 1 AND 5),
    is_selectable BOOLEAN      NOT NULL DEFAULT FALSE,      -- apuntable (hoja + nivel >= 4)
    is_active     BOOLEAN      NOT NULL DEFAULT TRUE,       -- activa/inactiva
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),      -- UTC (constitución: timestamps UTC)
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),      -- UTC (constitución: timestamps UTC)
    -- Multi-tenancy estricto: tenant en índice/clave (constitución III)
    CONSTRAINT uq_account_plan_tenant_id   UNIQUE (tenant_id, id),
    CONSTRAINT uq_account_plan_tenant_code UNIQUE (tenant_id, code),
    CONSTRAINT uq_account_plan_tenant_name UNIQUE (tenant_id, name),
    -- FK a la tenancy del sistema (empresa activa; tabla `companies` definida en
    -- SPEC-003). El plan se elimina en cascada con la empresa y queda aislado por ella.
    CONSTRAINT fk_account_plan_tenant FOREIGN KEY (tenant_id)
        REFERENCES companies (company_id) ON DELETE CASCADE,
    -- Jerarquía internamente multi-tenant: el padre se referencia por (tenant_id, id),
    -- lo que impide a nivel de CLAVE que una cuenta cuelgue de un padre de otra empresa
    -- (refuerzo de la constitución III a nivel de datos).
    CONSTRAINT fk_account_plan_parent FOREIGN KEY (tenant_id, parent_id)
        REFERENCES account_plan (tenant_id, id)
);

-- Índices multi-tenant: tenant_id SIEMPRE en cabeza (constitución III)
CREATE INDEX IF NOT EXISTS ix_account_plan_tenant        ON account_plan (tenant_id);
CREATE INDEX IF NOT EXISTS ix_account_plan_tenant_parent ON account_plan (tenant_id, parent_id);
CREATE INDEX IF NOT EXISTS ix_account_plan_tenant_level  ON account_plan (tenant_id, level, is_selectable);
CREATE INDEX IF NOT EXISTS ix_account_plan_tenant_code   ON account_plan (tenant_id, code);
-- Autocompletar por nombre (Fragmento) — pg_trgm para búsqueda ILIKE eficiente (SC-002 < 1s)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX IF NOT EXISTS ix_account_plan_name_trgm
    ON account_plan USING gin (name gin_trgm_ops);

COMMIT;
```

Notas:

- `tenant_id` se incluye en TODOS los índices compuestos como primera columna:
  toda consulta filtra por la empresa activa derivada de la sesión (constitución III),
  jamás por datos no confiables del cliente.
- La FK de tenancy (`tenant_id` → `companies.company_id`, definida en SPEC-003) y la FK
  jerárquica compuesta `(tenant_id, parent_id)` garantizan el aislamiento a nivel de
  datos (constitución III), no solo por disciplina de aplicación.
- `created_at`/`updated_at` son `TIMESTAMPTZ` UTC (constitución: timestamps UTC).
- Las columnas de importe (`NUMERIC(18,4)`) pertenecen a `journal_entry_line`; la tabla
  de cuentas no contiene importes.
- La auditoría de escrituras sobre el plan se define en §5.e (log inmutable, misma
  transacción ACID).

## 4. Seeding automático por tenant

Se ejecuta **automáticamente cada vez que se crea una nueva empresa/tenant**, dentro
de la misma transacción ACID que crea la empresa (constitución: operaciones atómicas).

Implementación:

1. **Trigger en la tabla de tenancy** (`companies` o equivalente) que, tras el INSERT
   de una empresa, invoca `seed_default_pgc(p_tenant_id)`.
2. **Idempotencia**: el seed verifica primero si el tenant ya tiene nivel 1 sembrado;
   si existe, no duplica (guarda ante reintentos de transacción).
3. **Auditoría (constitución II)**: el seed registra su ejecución en `audit_log`
   (§5.e) con actor `system`/`data_seed` e `ip = NULL`, en la misma transacción ACID
   que crea la empresa y siembra el catálogo.

```sql
-- ============================================================
--  SEED: catálogo base del PGC por tenant
-- ============================================================

    IF EXISTS (SELECT 1 FROM account_plan

-- Trigger de seeding automático al crear una empresa
CREATE OR REPLACE FUNCTION trg_companies_seed() RETURNS trigger AS $$
BEGIN
    PERFORM seed_default_pgc(NEW.company_id);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_companies_seed ON companies;
CREATE TRIGGER trg_companies_seed AFTER INSERT ON companies
    FOR EACH ROW EXECUTE FUNCTION trg_companies_seed();
```

> El trigger se ejecuta en la misma transacción que el INSERT de la empresa, cumpliendo
> la atomicidad; si el seed falla, la creación de la empresa se revierte completa.
> Alternativa recomendada a nivel de aplicación: invocar `seed_default_pgc` desde el
> servicio de alta de empresa dentro del mismo `async with async_session.begin()`.

## 5. Restricciones de validación: solo subcuentas `is_selectable = true` postean

La integridad se garantiza en el punto más cercano a la persistencia
(constitución I), con **constraints/triggers en PostgreSQL**, además de la lógica en
FastAPI.

### a) Reglas de estructura del plan (tabla `account_plan`)

Se añade una función de validación invocada por trigger que impone: código numérico,
nivel = longitud (niveles 1-4 / nivel 5 de 5-8 dígitos), profundidad ≤ 5, prefijo
padre, y `is_selectable` solo en hojas de nivel ≥ 4.

```sql
CREATE OR REPLACE FUNCTION chk_account_plan_structure() RETURNS trigger AS $$
DECLARE
    p_count INT;
BEGIN
    -- Solo dígitos
    IF NEW.code !~ '^[0-9]+$' THEN
        RAISE EXCEPTION 'account_plan: código debe ser numérico (%/%)', NEW.tenant_id, NEW.code;
    END IF;
    -- Nivel = longitud (1-4) o nivel 5 con 5-8 dígitos
    IF (NEW.level BETWEEN 1 AND 4 AND length(NEW.code) <> NEW.level)
       OR (NEW.level = 5 AND (length(NEW.code) < 5 OR length(NEW.code) > 8)) THEN
        RAISE EXCEPTION 'account_plan: nivel/longitud inconsistentes (code=%, level=%)', NEW.code, NEW.level;
    END IF;

    IF NEW.parent_id IS NOT NULL THEN
        -- Padre debe existir, ser de la MISMA empresa (multi-tenant) y nivel = nivel hijo - 1
        IF NOT EXISTS (SELECT 1 FROM account_plan
                       WHERE id = NEW.parent_id
                         AND tenant_id = NEW.tenant_id
                         AND level = NEW.level - 1
                         AND is_active = TRUE) THEN
            RAISE EXCEPTION 'account_plan: padre inválido o de otra empresa (parent=%, level=%)', NEW.parent_id, NEW.level;
        END IF;
        -- Prefijo jerárquico (código hija empieza por el del padre)
        IF NOT EXISTS (SELECT 1 FROM account_plan p
                       WHERE p.id = NEW.parent_id AND NEW.code LIKE p.code || '%') THEN
            RAISE EXCEPTION 'account_plan: el código hija no hereda el prefijo del padre (%)', NEW.code;
        END IF;
    ELSIF NEW.level <> 1 THEN
        RAISE EXCEPTION 'account_plan: cuenta de nivel % sin padre', NEW.level;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_account_plan_structure ON account_plan;
CREATE TRIGGER trg_account_plan_structure
    BEFORE INSERT OR UPDATE ON account_plan
    FOR EACH ROW EXECUTE FUNCTION chk_account_plan_structure();
```

### b) Mantenimiento automático de `is_selectable`

Al insertar una hija, la madre pierde su condición de hoja y pasa a
`is_selectable = false` de forma atómica en la misma transacción.

```sql
CREATE OR REPLACE FUNCTION sync_account_plan_selectable() RETURNS trigger AS $$
DECLARE
    v_new_parent BOOLEAN;
BEGIN
    -- Si el padre existe y ahora tiene hijas -> ya no es apuntable
    IF NEW.parent_id IS NOT NULL THEN
        UPDATE account_plan
           SET is_selectable = FALSE, updated_at = now()
         WHERE id = NEW.parent_id AND tenant_id = NEW.tenant_id;
    END IF;
    -- La cuenta recién insertada es hoja: apuntable solo si nivel >= 4
    IF (TG_OP = 'INSERT') THEN
        UPDATE account_plan
           SET is_selectable = (NEW.level >= 4)
         WHERE id = NEW.id AND tenant_id = NEW.tenant_id;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_account_plan_selectable ON account_plan;
CREATE TRIGGER trg_account_plan_selectable
    AFTER INSERT OR UPDATE OF parent_id ON account_plan
    FOR EACH ROW EXECUTE FUNCTION sync_account_plan_selectable();
```

### c) Protección de cuentas con movimiento (constitución II / inmutable)

Se impide a nivel de base de datos el borrado o la desactivación de una cuenta con
asientos asociados, y el borrado físico de cualquier cuenta del plan (la API no
expone DELETE; la restricción es a nivel defensivo de datos).

```sql
CREATE OR REPLACE FUNCTION chk_account_plan_protected() RETURNS trigger AS $$
DECLARE
    v_used INT;
BEGIN
    SELECT count(*) INTO v_used
      FROM journal_entry_line l
     WHERE l.account_id = OLD.id AND l.tenant_id = OLD.tenant_id;

    IF TG_OP = 'DELETE' THEN
        IF v_used > 0 OR EXISTS (SELECT 1 FROM account_plan c
                                  WHERE c.parent_id = OLD.id
                                    AND c.tenant_id = OLD.tenant_id) THEN
            RAISE EXCEPTION 'account_plan: no se puede eliminar la cuenta (tiene imputaciones o hijas)';
        END IF;
        RETURN OLD;
    END IF;

    IF TG_OP = 'UPDATE' AND (OLD.is_active = TRUE AND NEW.is_active = FALSE) AND v_used > 0 THEN
        RAISE EXCEPTION 'account_plan: no se puede desactivar una cuenta con asientos asociados';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_account_plan_protected ON account_plan;
CREATE TRIGGER trg_account_plan_protected
    BEFORE UPDATE OR DELETE ON account_plan
    FOR EACH ROW EXECUTE FUNCTION chk_account_plan_protected();
```

### d) Regla clave del Libro Diario

**Únicamente las cuentas con `is_selectable = true` y `is_active = true` pueden recibir
apuntes contables.** Se impone en el trigger de `journal_entry_line` (tabla del motor
de asientos, SPEC-002), en el punto de persistencia.

```sql
CREATE OR REPLACE FUNCTION chk_journal_line_account_selectable() RETURNS trigger AS $$
DECLARE
    v_bad INT;
BEGIN
    -- La cuenta debe pertenecer a la MISMA empresa y ser apuntable y activa
    SELECT count(*) INTO v_bad
      FROM account_plan a
     WHERE a.id = NEW.account_id
       AND a.tenant_id = NEW.tenant_id
       AND a.is_selectable = TRUE
       AND a.is_active = TRUE;

    IF v_bad = 0 THEN
        RAISE EXCEPTION
          'journal_entry_line: la cuenta % no es apuntable o no pertenece a la empresa (tenant %)',
          NEW.account_id, NEW.tenant_id;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_journal_line_account_selectable ON journal_entry_line;
CREATE TRIGGER trg_journal_line_account_selectable
    BEFORE INSERT OR UPDATE OF account_id ON journal_entry_line
    FOR EACH ROW EXECUTE FUNCTION chk_journal_line_account_selectable();
```

> Además, el balance estricto (Sum Debe == Sum Haber) y la atomicidad cabecera+línea se
> validan en el motor de asientos (SPEC-002 / constitución I), no duplicados aquí.

### e) Auditoría inmutable y en la misma transacción ACID

La constitución exige que **cada operación de escritura** quede registrada en un log
de auditoría **inmutable** (usuario, timestamp UTC, IP, operación y payload de la
entidad), persistido en la **misma transacción ACID** que la operación, y que no pueda
omitirse. Este plan lo declara explícitamente (no como simple nota):

```sql
-- ============================================================
--  audit_log: log de auditoría inmutable (WORM), multi-tenant
--  Registra usuario, UTC, IP, operación y payload en la misma
--  transacción ACID de la operación (constitución: auditoría).
-- ============================================================
CREATE TABLE IF NOT EXISTS audit_log (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id  BIGINT      NOT NULL,                       -- empresa afectada (aislamiento)
    actor      VARCHAR(200) NOT NULL,                      -- usuario ('system' para seed)
    action     VARCHAR(100) NOT NULL,                      -- CREATE / POST / UPDATE / REVERSAL / SEED_PGC ...
    entity     VARCHAR(100) NOT NULL,                      -- 'account_plan', 'company', ...
    entity_id  BIGINT,                                     -- id de la entidad afectada (opcional)
    ip         INET,                                       -- IP origen (null en procesos batch/seed)
    payload    JSONB,                                      -- delta/payload de la entidad
    created_at TIMESTAMPTZ  NOT NULL DEFAULT now()         -- UTC
);

-- Índices multi-tenant (constitución III): tenant siempre en cabeza
CREATE INDEX IF NOT EXISTS ix_audit_log_tenant        ON audit_log (tenant_id);
CREATE INDEX IF NOT EXISTS ix_audit_log_tenant_action ON audit_log (tenant_id, action, created_at);

-- Inmutabilidad del log: PROHIBIDO UPDATE y DELETE (WORM)
CREATE OR REPLACE FUNCTION chk_audit_log_immutable() RETURNS trigger AS $$
BEGIN
    RAISE EXCEPTION 'audit_log: el log de auditoría es inmutable (operación % denegada)', TG_OP;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_audit_log_immutable ON audit_log;
CREATE TRIGGER trg_audit_log_immutable
    BEFORE UPDATE OR DELETE ON audit_log
    FOR EACH ROW EXECUTE FUNCTION chk_audit_log_immutable();
```

Normas que se derivan del diseño anterior:

1. **Escritura obligatoria**: el alta, edición, desactivación de cuentas y el seed
   (`seed_default_pgc`) insertan su fila en `audit_log` dentro del mismo bloque
   transaccional (`async with async_session.begin()`); un fallo de auditoría aborta la
   operación completa (no puede omitirse).
2. **Payload sin `float`**: el `payload` JSONB serializa importes como cadenas decimales
   (`Decimal → str`) y nunca con tipos flotantes, en línea con la prohibición de la
   constitución para importes contables.
3. **Actor del seed**: las inserciones del catálogo se registran con el actor
   `system` (o `data_seed`) y `ip = NULL`, conservando trazabilidad sin asumir sesión
   de usuario.
4. **Sin `DELETE`/`UPDATE`**: el trigger `trg_audit_log_immutable` garantiza a nivel DB
   la inmutabilidad del registro (constitución: log inmutable), refuerzo de cualquier
   política de API.

## 6. Cumplimiento de la constitución

| Principio | Aplicación en este plan |
|-----------|--------------------------|
| III · Multi-tenancy estricto | `tenant_id` en PK/índices/filtros de toda consulta y trigger (`WHERE tenant_id = ...`); validación idéntica, incluso en triggers; FLUJO siempre filtra por empresa activa de sesión. |
| I · Partida doble / balance | Se delega en el motor de asientos (SPEC-002); aquí solo se garantiza que la cuenta posteada sea apuntable (triggers `is_selectable`). |
| II · Inmutabilidad | No DELETE físico por API; triggers protegen cuentas con asientos; timestamps UTC. |
| II · Auditoría | `audit_log` inmutable (WORM §5.e) con actor, UTC, IP y payload; se escribe en la misma transacción ACID que el seed y las operaciones del plan; prohibido omitirlo. |
| V · Pruebas obligatorias | Se agregan pruebas (pytest) de aislamiento entre empresas y de jerarquía/apuntabilidad (ver §7). |
| Precisión | Código/longitud controlados; cualquier importe en `NUMERIC(18,4)`; el `payload` de auditoría serializa importes como cadenas decimales (sin `float`). |
| Frontend | Árbol y autocompletar (teclado) consumen endpoints; la validación de apuntabilidad es informativa en UI, obligatoria en backend/DB. |

## 7. Estrategia de pruebas automatizadas (pytest)

1. **Aislamiento multi-tenant**: la empresa A no consulta, modifica ni elimina cuentas
   de la empresa B (SC-001): test directo + test de forzado por ID.
2. **Jerarquía / niveles**: alta de subcuenta respeta nivel padre+1; rechazo en nivel 5
   (FR-006) y de códigos duplicados por empresa (FR-004).
3. **Apuntabilidad**: solo hojas nivel ≥ 4 son `is_selectable`; al insertar hija, la
   madre deja de ser apuntable (SC-005).
4. **Trigger del diario**: insertar una `journal_entry_line` sobre cuenta no apuntable
   o de otra empresa → EXCEPTION verificada.
5. **Seeding**: crear empresa → catálogo 7 grupos sembrado; reintento idempotente; entrada de auditoría (`SEED_PGC`) en la misma transacción.
6. **Protección**: desactivar/borrar cuenta con asientos → EXCEPTION (SC-004).
7. **Auditoría inmutable**: intentos de `UPDATE`/`DELETE` sobre `audit_log` → EXCEPTION; cada escritura de cuenta deja su entrada de auditoría.

## 8. API / endpoints previstos (FastAPI, contrato)

| Método | Ruta | Función |
|--------|------|---------|
| GET | `/api/v1/accounts/tree` | Árbol de cuentas de la empresa activa |
| GET | `/api/v1/accounts/suggest?q=` | Autocompletar (solo `is_selectable=true`, tenant activo), < 1s (SC-002) |

Toda petición transporta el `tenant_id` de sesión; el backend lo deriva del contexto
autenticado y excluye cualquier ID del body (constitución III).
